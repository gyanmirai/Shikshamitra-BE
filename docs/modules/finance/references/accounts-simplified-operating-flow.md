# Simplify the Finance and Accounts operating flow

TL;DR: organize Fees and Accounts around the finance officer's real work, keep setup forms short, add missing Student Accounts and Fee Demands workspaces, separate payment verification from bank reconciliation, and let the backend create journals automatically.
This page is an active target design based on the reviewed implementation.
Routes and APIs marked as target are not statements of shipped behavior.

Team walkthrough: [editable Excalidraw flow](./school-finance-management-flow.excalidraw) and [PNG preview](./school-finance-management-flow.png). The diagram combines the proposed Fees and Accounts journey with an INR-based school payment example.

Earlier team walkthrough: [editable screen-and-form Excalidraw map](./school-finance-management-detailed.excalidraw) and [PNG preview](./school-finance-management-detailed.png). Its detailed field labels predate the simplification in this document; use the field decisions below as the current proposal. Its arrows are reading order; optional fee actions are not mandatory workflow stages.

## Product goal

A finance officer should understand these business actions:

```text
Assign fees
Raise a demand
Collect money
Grant an approved reduction
Move an available credit
Return money
Record other income
Record an expense
Verify a payment
Match the bank statement
```

The finance officer should not need to construct debit and credit lines for routine work.
The backend resolves policies, accounting mappings, periods, journals, and audit evidence.
**Accounts Settings and Accounts transactions have no policy-selection field.** Fee policies are configured once under Policies & Rules and resolved by the Fees backend where they apply. Accounts receives the resulting approved financial event and posts it; it never asks which Collection, Concession, Refund, or Proration Policy to use.

## Form-design rule: ask only what a person knows

Do not add a manual **Code** field to Account Heads or Fee Heads. Neither current form has one; preserve that good choice. An internal database ID is still necessary, but it is never a finance-officer input. If an external accounting export later needs a numbering scheme, generate and manage it internally or in a separate administrator-only import mapping.

Use three layers consistently:

| Layer | Examples | Presentation |
|---|---|---|
| Required business input | Name, category, amount, student, actual bank details, payment method, reason when changing money | Show on the relevant form |
| Conditional input | Transaction reference for an electronic payment, evidence when a policy requires it, payout bank, approval reason, special fee-head linkage | Show only when that choice or policy applies |
| System-owned control | IDs, codes, version numbers, journal numbers, timestamps, row/concurrency stamps, preview fingerprints, idempotency keys, account mapping version, debit/credit lines, derived status and totals | Generate, validate and audit in the backend; show read-only details to accountants when useful |

Do not hide a real accounting decision merely to shorten a form. A refundable deposit versus tuition must be classified correctly, and a bank payout must name the actual bank account. Prefer a plain-language choice, a safe default, and an impact preview over exposing technical fields. A required field is justified only if it changes a business outcome, is needed to make or trace a payment, or is required by a real policy or legal obligation.

**Asset** in Account Head is an accounting type for cash, bank, receivables, and similar balances; it is not an Asset Management module. **Library** is an optional source-module link on a Fee Head, not an Account Head type. Ordinary tuition or transport setup should not require an Asset or Library option. Show a Library link only when a fee is actually generated by Library workflows.

### Existing forms reviewed and exact simplifications

| Screen | Current implementation | Updated officer-facing form | Required implementation change |
|---|---|---|---|
| Account Head | Name, type, optional parent, notes; **no code** | Keep name and type; parent only for grouping; notes optional | Do not add code, currency, posting permission, reconciliation flag, or effective-date controls. Protect seeded control heads in the backend. |
| Fee Head | Fee category, name, optional module, concession switch, mandatory income category, description; **no code** | Fee category, name, plain-language treatment (normal fee or refundable deposit), concession eligibility when relevant; description optional | Default income category from fee category. Require an explicit accounting category only when no safe default exists or an administrator overrides it. Show module only for a real Library/Transport/etc. integration, not every fee head. Do not add code or policy selection. |
| Fee Category with embedded Fee Heads | Category name and description; embedded heads repeat name, income category, module, concession, description | Category name; description optional; add heads by name with inherited defaults | Reuse the same Fee Head rules in both creation paths so one path does not force extra fields or bypass accounting validation. |
| Income/Expense Category | Name, mandatory default account head, **mandatory tags**, optional description | Name and matching account head; description optional | Make tags optional and keep them outside the primary form unless a real reporting feature uses them. Preserve the account mapping because it controls posting. |
| Bank Account | Manual **Code**, bank/branch/account details, IFSC, dates, purpose, UPI ID, asset account head | Bank name, account holder, account number, IFSC, branch if operationally needed; optional UPI ID; clear display name | Generate an internal bank code server-side if legacy/export logic needs it. Default/create the linked asset head safely or require accountant confirmation. Default effective-from to today; show end date only for planned retirement. Keep actual account number and IFSC. |
| Payment Mode | Proposed shared configuration | Mode name and active status in ordinary setup; conditional reference/settlement settings for an administrator | Seed Cash, Bank Transfer, Cheque, UPI, Card and Gateway defaults. Do not ask an officer to configure clearing accounts on every transaction. |

These are target changes, not claims that the current frontend or backend has already been modified.

## Role-based experience

| Role | Main modules | Restricted functions |
|---|---|---|
| Finance officer | Student Accounts, Demands, Collections, Receipts, Income, Expenses, Payment Verification, Bank Reconciliation | Raw mapping activation, opening balances, manual journals, period reopen |
| Finance approver | Concessions, Adjustments, Refunds, expense approvals, exception approvals | Cannot approve their own request where maker-checker applies |

| Auditor | Reports, Audit Trail, source-to-journal drill-down | Read-only |

## One-time setup flow

```text
Accounts setup (accountant):
  Confirm seeded Account Heads -> Link Bank Accounts -> Confirm Payment Modes
  -> Map Income/Expense Categories -> Review automatic posting defaults

Fees setup (fees administrator):
  Fee Categories/Heads -> Payment Terms -> Fee Structure
  -> Publish -> Assign to students

Policies & Rules setup (authorized finance administrator):
  Configure Collection/Concession/Refund/Proration rules once
  -> Activate rules for their scope; no Accounts-side policy selection

System readiness:
  Check required account mappings and applicable fee rules
  -> Show any missing setup to its owning team
  -> Begin transactions; each module resolves its own applicable configuration
```

The system should seed a standard school chart of accounts and fixed posting templates.
An accountant confirms mappings instead of designing accounting rules from scratch. Opening Balances is a separate migration-only step if historical balances must be brought in. A missing or ambiguous policy blocks the affected Fees action with a clear setup error; it does not send an officer to Accounts Settings to choose one.

## Accounts settings

This section has **no Collection, Concession, Refund, or Proration Policy dropdown**, no policy assignment, and no `PolicyId` request field. The only connections to Fees are account mappings: where a fee demand, collection, concession, waiver, advance, or refund posts after Fees has calculated and approved it. Accounting Mappings are not business-policy selectors.

### Account Heads

Retain the existing form: **Head Name** and **Head Type** are required; **Parent Account Head** and **Notes** are optional. Preserve the existing hierarchy, status, dependency checks, history, and server-side concurrency protection. Do not add a Code field or require the officer to choose posting behavior, reconciliation settings, effective dates, or currency. Seeded control-account roles and posting eligibility are backend-owned; an authorized accountant can inspect them read-only. Parent must be the same type, must not create a cycle, and cannot be switched in a way that changes posted history. The user sees a reasoned dependency warning before deactivation.

Minimum system accounts are:

| Purpose | Type |
|---|---|
| Cash in hand | Asset |
| School bank account | Asset |
| Student fee receivable | Asset |
| Cheque, UPI, card, and gateway clearing | Asset |
| Student advance | Liability |
| Student refund payable | Liability |
| Refundable student deposit | Liability |
| Fee income accounts | Income |
| Concession and fee refund | Contra-income or approved expense treatment |
| Operating expenditure accounts | Expense |

System control accounts are selected by backend mappings and are not available as ordinary manual transaction choices. For example, a fee officer should select **Tuition Fee**, not manually select **Student Fee Receivable** or enter an account number. The backend retains immutable IDs and historical account snapshots without asking for an invented account code.

### Income and Expense Categories

Retain the existing category-to-default-account mapping.
Keep the visible form to **Category Name**, **Default Income/Expense Account Head**, and optional **Description**. The account selector is an actual accounting decision and remains required for an accountant setting up a category. Remove mandatory Tags from the frontend validation; tags can stay as optional metadata if reports truly use them. Do not introduce a manual category code or version/date fields.
Add server-side downstream usage and accounting-readiness checks, without adding setup inputs.
An already-used mapping is superseded instead of rewriting historical transactions.

### Bank Accounts

Retain the existing Bank Account to Asset Account Head relationship.
The current Bank Account form requires a manual **Code** and **Effective From**; those are not suitable primary inputs. Generate any required internal code in the backend. Default the start date to creation/activation, and request an end date only when retiring a bank account. Keep bank name, account holder, account number, and IFSC because they identify where money actually moves. Branch name remains only if the bank/operational process needs it; branch address, purpose, and UPI ID are optional. The asset account link is required for posting but should be suggested or auto-created with the bank; an accountant confirms an exception, not every officer.
Add reconciliation enablement, pending dependency counts, and separately audited sensitive-detail access as system/administrative behavior, not routine form fields.
Refund and expense payouts use `BankAccountId` instead of free-text bank information.

### Payment Modes

Use one canonical configuration across Collections, Income, Expenses, Refunds, and Reconciliation.

| Mode | Initial account | Initial state |
|---|---|---|
| Cash | Cash in hand | Settled |
| Bank transfer | Selected bank | Settled or pending confirmation |
| Cheque | Cheque clearing | Pending verification |
| UPI | UPI clearing | Pending settlement |
| Card | Card clearing | Pending settlement |
| Gateway | Gateway clearing | Pending settlement |
| Wallet | Wallet clearing | Pending settlement |

The system seeds each mode's reference requirements and verification/settlement behavior. The routine user chooses only the payment mode, relevant bank, and a reference when that mode needs one. Effective dates and clearing-account settings belong in a restricted administrator view only if a real change is required.

### Accounting Mappings

Replace the current hardcoded Posting Automation surface with seeded, controlled system-event mappings. Do not expose a generic programming or expression builder or require a finance officer to enter debit and credit rules. The following table explains backend behavior to the team; it is **not** a daily form.

| Event | Debit source | Credit source |
|---|---|---|
| Fee demand | Student fee receivable | Fee-head account |
| Fee collection | Payment-mode account | Student fee receivable |
| Instrument settlement | Selected bank | Clearing account |
| Concession | Concession account | Student fee receivable or refund payable |
| Waiver | Waiver account | Student fee receivable |
| Student advance receipt | Payment-mode account | Student advance |
| Advance allocation | Student advance | Student fee receivable |
| Refund payout | Refund payable or student advance | Selected bank |
| Other income | Cash, bank, or receivable | Income-category account |
| Expense payment | Expense-category account or payable | Cash or bank |

Mappings have Draft, Active, and Retired states internally. Active versions are immutable after use. Only a finance administrator/accountant sees a human-readable mapping summary and a **Simulate example** action before approval/activation. Version IDs, event keys, and effective timestamps are recorded by the backend.

### Opening Balances

Opening Balances is an administrator-only onboarding and migration workspace.
It creates one approved opening journal and cannot become a general transaction-entry shortcut.
The screen requires a balancing equity or opening-fund account, import preview, error report, approval, and immutable posting evidence.

## Policy ownership

All four policies live under **Policies & Rules**, outside Accounts Settings. An authorized administrator defines an active rule for the relevant school/academic-year/fee-head scope. Fees automatically resolves the one applicable rule by transaction date and context, validates its result, and records the resolved rule/version in audit history. If no rule or multiple equally applicable rules exist, Fees returns a configuration error; it must not silently choose one. The officer sees the outcome and explanation, not a dropdown. Accounts only receives the approved amount, source, classification, and immutable policy provenance for read-only audit.

### Collection Policy

Collection Policy owns late-fee calculation, grace period, rounding, eligible fee heads, direct collection waiver behavior, approval thresholds, and online collection eligibility.
Add explicit partial-payment, split-payment, future-installment, overpayment, allocation-priority, provisional-payment, reversal-window, and chargeback behavior.
The policy screen should present these as a few business questions with safe defaults (for example, **Allow partial payments?**, **What happens to extra money?**, **Who can waive late fees?**), with advanced overrides collapsed. Do not ask an officer to type policy IDs, version numbers, expression code, or accounting accounts.

### Concession Policy

Concession Policy owns eligibility, calculation, limits, fee-head scope, evidence, effective version, and application behavior.
The Concession Request records the automatically resolved policy/version.
Remove a Fee Structure policy picker if its value is currently accepted and discarded. The concession rule should resolve automatically from the approved scope; any future explicit exception requires a documented business case and a restricted Fees-side override, never an Accounts setting. The user chooses a named concession type and enters an amount or percentage plus reason/evidence when required; policy version and limits are resolved by the server.

### Refund Policy

Refund Policy owns refundable sources, fee-head scope, paid-charge and late-fee treatment, partial refund, caps, deductions, payout methods, and processing target.
Accounting treatment is derived from the original source: advance, deposit, recognized fee, or post-payment concession.
The requester sees the **maximum refundable amount** and chooses a permitted amount and reason. They do not choose a debit account or manually label the refund as an expense.

### Proration Policy

Proration Policy owns fee-head rules, cutoff, minimum charge days, rounding, and after-cutoff behavior.
Proration before demand changes the generated amount.
Proration after demand creates a traceable demand reduction or reversal rather than overwriting history.
Use the automatically applicable rule and a plain-language preview; the officer does not select a policy or edit a calculation formula or effective-version ID in an assignment form.

## End-to-end Fees flow

### 1. Configure and publish

```text
Fee Category
-> Fee Head with accounting classification
-> Payment Term
-> Fee Structure preview
-> Accounting readiness
-> Publish immutable version
```

The preview checks the automatically applicable Fees rules. It does not require a policy selection on the Fee Structure or any Account setting.

The Fee Head form uses a plain-language **Treatment** choice only when needed: **School fee income** (default), **Refundable deposit**, or **Collected for another party**. An advance is normally the result of receiving more money than currently due, not a Fee Head type. A refundable security deposit maps to a Liability rather than Fee Income. The current Fee Head contract requires `IncomeCategoryId` for every head, so this change needs a deliberate DTO, validation, mapping, and migration path: ordinary fees inherit a valid income category; deposits and pass-through items resolve to a liability mapping. Do not merely hide a still-required blank field in the UI or assign a fake income category. If an existing Fee Category cannot supply a unique safe default, keep the accounting choice visible to an authorized setup user until that category is configured.

### 2. Assign the fee structure

Fees > Fee Structure Assignment retains the current preview token, fingerprint, enrollment validation, and transactional commit.
The assignment pins structure, payment-term, collection, refund, and proration versions.
It creates immutable installment schedules and reports accounting readiness.

### 3. Generate the fee demand

Fees > Fee Demands shows Scheduled, Generated, Partially Paid, Paid, Cancelled, and Reversed demands.
Demand generation is idempotent and creates a numbered demand plus fee-head lines.

Example:

```text
Tuition demand:   INR 12,000
Transport demand:  INR 3,000
Total:            INR 15,000
```

Automatic journal:

```text
Dr Student Fee Receivable    INR 15,000
Cr Tuition Fee Income        INR 12,000
Cr Transport Fee Income       INR 3,000
```

Demand cancellation creates a linked reversal.
A paid demand cannot be deleted or silently cancelled.

### 4. Review the Student Account

Fees > Student Accounts is the consolidated student subledger.
It shows demands, charges, collections, allocations, concessions, waivers, adjustments, advances, refunds, reversals, running due, and running credit.
Every row links to its source document, receipt, policy version, approval history, and journal.
The student subledger remains distinct from the General Ledger but reconciles to its control accounts.

### 5. Collect fees

Fees > Collections uses this guided flow:

```text
Find student
-> Review open demands and charges
-> Select payment allocations
-> Add payment instruments
-> Review backend-calculated impact
-> Confirm collection
-> Show receipt, posting, and verification result
```

The review shows amount received, current-due allocation, future allocation, student advance, remaining outstanding, and instruments awaiting verification.

Split payment example:

```text
Cash: INR 4,000
UPI:  INR 6,000

Dr Cash in Hand               INR 4,000
Dr UPI Clearing               INR 6,000
Cr Student Fee Receivable    INR 10,000
```

### 6. Verify provisional instruments

Accounts > Payment Verification works at Payment Instrument level.
It supports Verify, Reject, Mark Failed, View Receipt, and View Evidence.

UPI settlement example:

```text
Dr School Bank                INR 6,000
Cr UPI Clearing               INR 6,000
```

Rejection reopens the affected student receivable and reverses only that instrument's financial effect.

### 7. Apply concession

Fees > Concessions preserves request, evidence, preview, submission, approval, application, rejection, cancellation, and reversal.
Approval preview shows original due, paid amount, concession, new outstanding, and created student credit or refund.

Unpaid-demand example:

```text
Dr Fee Concession             INR 1,000
Cr Student Fee Receivable     INR 1,000
```

Paid-demand concession creates Student Refund Payable instead of a negative due.

### 8. Apply direct waiver

The eligible late-fee or charge row exposes Waive inside Collections.
The finance officer supplies a mandatory reason and the backend calculates the full current eligible balance.
The action follows Collection Policy and approved override authority.

```text
Dr Late Fee Waiver              INR 500
Cr Student Fee Receivable       INR 500
```

### 9. Apply adjustment

Fees > Adjustments selects a genuine credit source first.
Valid sources are Student Advance, settled overpayment, and approved credit note.
Outstanding unpaid dues are not available credit.

```text
Available student advance: INR 2,000
Transport outstanding:     INR 3,000

Dr Student Advance            INR 2,000
Cr Student Fee Receivable     INR 2,000
```

The backend consumes the source and credits targets atomically.

### 10. Process refund

Fees > Refunds preserves the current request, review, approval, reservation, processing, failure, cancellation, and reversal lifecycle.
The payout form asks for bank account, method, settlement date, reference, and evidence.

Advance refund:

```text
Dr Student Advance            INR 1,000
Cr School Bank                INR 1,000
```

Recognized fee refund approval and payout:

```text
Dr Fee Refund                 INR 2,000
Cr Student Refund Payable     INR 2,000

Dr Student Refund Payable     INR 2,000
Cr School Bank                INR 2,000
```

Refund does not create an ordinary Expense record.

## End-to-end Accounts flow

Accounts has one simple transaction path:

```text
Officer records other income or an expense, or opens a Fees-originated item
-> System validates the business source, payment details, permission, and open period
-> System chooses accounts from category/bank/payment-mode mappings
-> Officer reviews amount, payee/payer, payment status, and plain-language effect
-> Approval if required -> automatic balanced journal -> ledger and bank/reconciliation view
```

There is **no policy step or policy selection** between these stages. For Fees-originated entries, Fees has already applied its Collection/Concession/Refund/Proration rule before sending the approved event. For other Income and Expenses, the user chooses a transaction category, not a fee policy; authorization, approval thresholds, and payment controls are enforced by their owning workflow and server configuration. An accountant may inspect which rule produced a Fees-originated amount in source details, read-only.

Example: a tuition concession of INR 1,000 is approved in **Fees > Concessions**. The Fees service checks the applicable concession rule and emits `ConcessionApplied` for INR 1,000. Accounts maps that event to `Dr Fee Concession / Cr Student Fee Receivable` and links the journal back to the request. The accountant does not choose a concession policy in Account Heads, Income Categories, Posting Mappings, or the journal screen. An INR 25,000 electricity bill follows **Accounts > Expenses**: choose Electricity, vendor, amount, date, and paid/payable; the category supplies the expense account. No fee policy is relevant.

### Income

Accounts > Income is for non-fee income only.
Fee collection is never entered again as Income.

```text
Select category
-> Enter payer, amount, date, description, reference, and evidence
-> Select cash, bank, or receivable destination
-> Review business and accounting impact
-> Submit or record
```

Donation example:

```text
Dr School Bank               INR 10,000
Cr Donation Income           INR 10,000
```

Statuses are Draft, Submitted, Approved, Posted, and Reversed.
Posted income cannot be edited or deleted.

### Expenses

Accounts > Expenses asks one understandable payment question:

```text
Has this expense already been paid?
- Yes: select cash or bank.
- No: record it as payable.
```

Immediate electricity payment:

```text
Dr Electricity Expense       INR 25,000
Cr School Bank               INR 25,000
```

Unpaid bill approval and later payment:

```text
Dr Electricity Expense       INR 25,000
Cr Vendor Payable            INR 25,000

Dr Vendor Payable            INR 25,000
Cr School Bank               INR 25,000
```

Statuses are Draft, Submitted, Approved, Payment Pending, Posted, and Reversed.

### Payment Verification

Payment Verification is operational acceptance of cheque, UPI, card, gateway, wallet, and other provisional instruments.
It is not bank-statement reconciliation.
Each decision targets one Payment Instrument and preserves other instruments in a split collection.

### Bank Reconciliation

Accounts > Bank Reconciliation follows this flow:

```text
Select bank and period
-> Import statement
-> Detect duplicate import
-> Review suggested matches
-> Match, partially match, or leave unresolved
-> Record genuine bank charges or interest through Expenses or Income
-> Review statement and system balance
-> Close reconciliation batch
```

A match never mutates the original collection to force agreement.

### Journals and Ledger

This workspace is primarily read-only for finance officers and fully visible to accountants and auditors.
It provides Journal List, Journal Detail, Account Ledger, Source Document, Reversal Link, and Posting Mapping Version.
Manual Journal is a separate restricted action for opening balances and exceptional accounting corrections.

### Posting Exceptions

Routine operations post automatically.
Posting Exceptions contains only records blocked by missing mapping, closed period, invalid account, migration anomaly, or recoverable processing failure.
Each exception shows business source, failure reason, financial effect, corrective action, retry result, and audit history.

### Period Close

Accounting periods are generated monthly from the financial year.
Finance officers see the current open period.
Authorized accountants see close preview, blockers, close, and audited reopen.

Close preview checks unposted events, posting exceptions, pending verification, unreconciled bank lines, draft journals, and pending high-risk approvals.

## Automatic backend accounting

The user performs one business command. A Fees command resolves and validates its applicable fee rule before creating the event; an Income/Expense command has no fee-rule lookup. The backend completes the accounting work:

```text
Validate permission, scope, state, amount, evidence, and period
-> For Fees only: resolve the applicable rule automatically, validate it, and retain provenance
-> Recalculate the authoritative preview
-> Verify preview fingerprint and row version
-> Persist the operational transition and immutable Financial Event
-> Resolve the active Accounting Mapping version
-> Create balanced Journal Entry and Journal Lines
-> Update rebuildable student and account projections
-> Commit atomically
-> Publish recoverable notification and document work
```

Daily screens never call a separate create-journal endpoint.
An idempotent retry returns the original result.

## Minimal operational forms and school examples

These are the fields the person actually enters. Summary cards show due, credit, eligibility, and resulting balance; their values are calculated, not editable. Search, filters, and read-only detail fields are not counted as transaction inputs.

| Screen/action | Required officer input | Conditional input only | Backend-calculated or hidden |
|---|---|---|---|
| Fee Structure | Name, academic year, applicable class/group, fee heads and amounts, installment plan | Optional fee head or exception | Structure ID/version, per-installment totals, applicable-rule readiness and mapping checks; no policy picker |
| Assignment | Student/group and published structure | Start date or proration reason when joining mid-year | Eligibility, installment dates, amounts, resolved rule versions, preview fingerprint; no policy picker |
| Fee Demand | Due installment(s) or scheduled generation batch | Reason for cancellation | Demand number, fee-head lines, status, journal, duplicate protection |
| Collection | Student, received amount, payment mode(s), allocation confirmation | Reference for UPI/transfer/cheque; bank when needed; advance decision when overpaid | Available dues, default oldest-due allocation, receipt number, advance, payment status and journal |
| Payment Verification | Select pending instrument and Verify/Reject/Failed | Failure reason and evidence if rejected/failed | Clearing release, affected receipt/dues, settlement journal |
| Concession | Student, named concession, amount or percentage, reason | Evidence and fee-head selection if policy requires; approval comment | Eligible cap, unpaid/paid split, revised due or refund payable, journal |
| Direct waiver | Eligible charge, reason | Approval/evidence when policy threshold requires | Full eligible waiver amount, remaining charge, journal |
| Adjustment | Student, available credit source, target due, amount, reason | Approval if threshold requires | Credit availability and consumption, due after transfer, journal |
| Refund | Student, refundable source, amount, reason | Payout bank and reference at payout; evidence when required | Eligible maximum, reservation, payable state, accounting treatment, journal |
| Other income | Category, payer/source, amount, date, received by cash/bank or still receivable | Bank, reference, receipt/evidence when applicable | Linked account head, voucher number, journal |
| Expense | Category, vendor/payee, amount, date, paid now or payable later | Bank/mode/reference for payout; invoice/evidence or approval as required | Linked account head, payable balance, voucher number, journal |
| Bank reconciliation | Bank account and statement period, import file, match decision | Explanation for an unmatched item or manual match | Duplicates, suggested matches, difference, close blockers |
| Period close | Period and Close action | Reopen reason for an authorized reopen | Readiness checks, totals, closed by/at, audit record |

For example, when Aarav pays INR 10,000 against INR 15,000 due, the officer selects Aarav, enters `10,000`, chooses `Cash INR 4,000` and `UPI INR 6,000`, then confirms the suggested allocation. They do **not** enter a fee-head code, account code, journal number, debit account, credit account, policy version, or idempotency key. The system shows INR 5,000 remaining due, a receipt, and the accounting entry in read-only details. When Meera has INR 2,000 advance and requests INR 1,000 back, the officer selects the existing advance, amount, reason, and payout bank; the system prevents a refund above available credit and posts a liability payout, not an expense.

## Acceptance gates

1. Every posted financial event produces exactly one balanced journal.
2. Routine finance work never requires manual debit and credit entry.
3. Posted history is immutable and every correction links to the original record.
4. Student outstanding equals the Student Fee Receivable control-account balance.
5. Student credits equal Student Advance and Student Refund Payable control balances.
6. Clearing-account balances equal unsettled payment instruments.
7. Bank ledger balances reconcile to closed statement batches.
8. Closed-period totals cannot change without an audited reopen.
9. The same command is safe to retry, while the same key with a different payload conflicts.
10. Every action enforces tenant, user scope, exact permission, and maker-checker rules.
11. No Accounts Settings or Accounts transaction request requires fee-policy selection; Fees resolves one applicable rule or returns a clear missing/ambiguous-rule error.
